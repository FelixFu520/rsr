# 采集结果验收与失败迭代

目标：正式目录里的每条数据都由真实物理产生、通过可测量的验收，并有一份不启动 Kit 的独立复核。

## 1. 设计验收项

在 `Planner.result()` 或 `Job._evaluate()` 里返回 `checks: dict[str, bool]`、`failed_checks`、
`success = all(checks.values())`，以及每项的实测值。门限放配置字段里，带单位。“动作序列走完”不算成功。

| 任务类型 | 本仓库用过的检查 |
|---|---|
| 刚体抓放 | 保持期抬升 ≥ 门限、保持期贴近夹爪、松开后回落、回落后受支撑、落点误差 ≤ 门限、无附件 |
| 柔体抓放 | 上述各项 + 无固定顶点、确实变形（形状 RMS > 3 mm）、边长拉伸 p99 / 最大值、三角形面积比、台面/指垫/地面穿透、袋内包含、子步接触容量未溢出、转运期双侧接触 ≥ 95% |
| 双臂/流水线 | 每次交接后全机器人无接触、完整受支撑、标签朝上、真实输送位移、先离带后落地、原生 mimic 子步残差 |
| 导航/巡检 | 路线与接近路径净空、目标发现、到达并对准、机身跟随指令（单步偏差 < 1 mm）、腿部跟踪误差、照片内容像素检查、报警时序 |
| 数据与渲染 | 采集前后物理步数（和 Flow 时间）不变、相机矩阵与分辨率一致、渲染同步像素审计 |

前置检查尽早失败：航点 A* 不通在 `arrange_scene` 报错并输出地图；Flow 预热后先检查火焰像素。
区分流程成功与严格质量成功时分别记录（分拣的 `workflow_success` / `strict_quality_success`），不能把前者写成后者。

## 2. 独立校验脚本

`scripts/<task>/validate_<task>.py <output_dir>`：只用 numpy、pyarrow、Pillow 和系统 ffmpeg/ffprobe，
写 `validation.json`（和 `qa/keyframes.jpg`），任一项失败返回非零。

- 通用部分可调用 `utils/lerobot_v3.validate_dataset`：`codebase_version`、帧号/时间戳等间隔、
  state/action 有限且维度与名称一致、每路视频帧数/fps/分辨率/H.264、完整解码、episode 时间范围、成功标签与 `dataset_use` 一致。
  它还假定 `observation.state` 前 7 维是机械臂关节（成功时要求最大变化 ≥ 0.1 rad），不符合的机型
  （移动底盘、足式、双臂顺序不同）要自写这部分检查。
- 任务部分从原始数据重新计算，不照抄 Job 的结论：例如按录制动作积分复现位移和航向；从照片重新数火焰像素；
  重新读物理源算拉伸、间隙、穿透；解码视频核对关键帧。
- 校验的是数据，不是代码路径：同一个函数可以被 Job 和校验脚本共用（如 `render_sync_audit_frames`），但输入要来自落盘文件。

## 3. 逐级推进

| 级 | 做什么 | 输出 | 进入下一级的条件 |
|---|---|---|---|
| 0 | 无 Kit 单元测试 | — | `pytest -q` 通过 |
| 1 | 世界模式冒烟 `validate_physics_modes.py` | 终端 / debug | 所选模式自由落体与只渲染检查通过 |
| 2 | 只跑物理、不录 RGB 的探针或检查脚本 | `outputs/debug/<task>/physics*/` | 物理验收全部通过 |
| 3 | 调试配置全流程（低 spp、可覆盖、失败也导出 diagnostic） | `outputs/debug/<task>/` | Job 验收与独立校验全部通过 |
| 4 | 正式配置 | `outputs/<task>/` | `success=true`，数据集为 `demonstration` |
| 5 | 独立校验 | `validation.json` | 全部通过 |
| 6 | 视觉复核：关键帧拼图、多路同步预览 | `qa/` | 实际查看过并写明范围；没看过就标 `pending_visual_inspection` |

长任务前先估时：用第 3 级的分项耗时外推正式运行时间，超过 1 小时的运行先告诉用户预计时长。
可以在后台运行并定期看日志与进程，不要重复启动仍在运行的工作进程。

## 4. 失败分析循环

1. **冻结证据**：`diagnostics/<run>/` 的 `configuration.json`、`result.json`、`trajectory.jsonl`、日志、失败帧，
   保留在 `outputs/debug/<task>/`，不覆盖。
2. **分类**：物理（滑脱、穿透、发散、拉伸）/ 控制与规划（IK 失败、路径不通、抓点错误）/
   渲染与数据（错帧、画面缺失、视频不可解码）/ 流程（超时、Kit 崩溃、资产缺失、配置字段错）。
3. **按直接证据定位**：看逐步 `rows`、接触统计、逐子步记录、相机矩阵；不要凭画面推断物理状态。
4. **最小对照实验**：同一初始状态，一次只改一个变量，跑在 debug 目录，记录每次运行的配置差异和结果。
5. **修根因**：不靠放宽门限、附着约束、瞬移、隐藏碰撞体或删除碰撞体换取通过。门限本身不合理时，
   给出证据请用户决定。
6. **回到第 2 或第 3 级重跑**，通过后再跑正式配置。
7. **写进文档**“问题与解决方案”：现象 / 原因 / 处理，失败过的方案也写。

GPU 求解（CUDA VBD、MuJoCo GPU）有运行间差异。边缘用例按“保持门限、重跑、全部记录”处理：通过的运行放正式目录，
其余放 debug，`run_note.json` 列出每次运行的输出目录和关键指标；用改动前的代码复跑以排除回归。

## 5. 本仓库踩过的坑（先对照再排查）

| 现象 | 原因 | 处理 |
|---|---|---|
| 机身速度是指令的数倍 | 规划器写入已积分位姿后 PhysX 再积分；提交时间轴时间变化会让 PhysX stage-update 节点多走一步 | 写当前参考位姿 + 速度；持有时间轴期间禁用该节点；加“机身跟随指令”检查 |
| 加机器人后状态读取失败 | 建图时的无机器人物理视图被缓存 | 建图后 `invalidate_physics()` |
| 机器人落到地面以下 | 资产根 prim 带站立高度，躯干 link 无偏移 | 按 link 相对根的变换反算根位姿 |
| 运动学校验失败 | `reset()` 把直腿姿态写回 USD | 在建立物理视图之前校验 |
| 材质大量编译错误 | MDL 依赖没复制 | 资产脚本递归解析 MDL |
| 脚本出错却返回 0 | Kit 快速退出吞掉异常 | 先记录，再 `close(exit_code=1)` |
| 多相机画面不一致或带网格 | 时域抗锯齿/DLSS 历史跨相机；视口叠加层 | FXAA、关 DLSS；无头关闭显示选项；核对相机矩阵 |
| 夹爪与包裹错帧 | PathTracing 累积早于刚体变换到达渲染器；GPU 被其它进程占用时更严重 | 同步采集屏障 + 同实例像素审计；正式渲染独占 GPU |
| 采集超时 | 高 spp × 多子帧，步进后还多渲染一次 | `step(render=False)`；记录分项耗时 |
| 已松手却仍被拱起 | 固定基座 `body_id=-1` 被当成世界静态体漏计 | 按机器人 shape 范围统计接触 |
| 60 Hz 记录正常、实际约束超限 | 子步尖峰被采样漏掉 | 逐子步记录并验收 |
| 抓深不准 | 用 TCP 或金属指尖推断指垫底边 | 用原生 FK 算指垫底边 |
| 夹指与布料可见间隙 | 粒子碰撞半径构成接触包络 | 记录为局限；接触验收与视觉零间隙是两回事 |

## 6. 结果记录与报告

- `result.json`：`success`、`checks`、`failed_checks`、各项实测值、`error`、`timings_s`、`physics_steps`、
  `simulation_time_s`、引擎与求解器、帧数、`dataset_use`；数据集 `meta/task_outcome.json` 含结果与生效配置。
- 正式目录只放通过的运行；批量采集脚本把失败目录移到 debug（参考 `collect_physic_solver_cases.py::_move_to_debug`）。
- 文档“当前结果”写采集日期（UTC）、关键实测值与门限、输出链接。
- 如实写未验证项：例如尚未用官方 LeRobot SDK 加载、人工视觉复核待做、几何检查只覆盖保存的物理帧。
